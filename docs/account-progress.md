# Прогресс аккаунта: синхронизация v1

10 ноября 2026. Реализованы серверное хранение и объединение тренировок, XP, обычных достижений и GPS-рекордов. Проверки на телефоне пользователь отложил; рабочий сервер этим этапом не перезапускается.

## Что видит пользователь

- Новая тренировка сначала сохраняется на устройстве вместе с очередью отправки. Отсутствие сети не отменяет запись.
- Синхронизация запускается при открытии приложения, возвращении в него, завершении тренировки и по кнопке **Прогресс → Обновить**. Статус показывает, сохранён ли прогресс в аккаунте или пока только на устройстве. При старом сервере показывается необходимость перезапуска.
- После входа на другом устройстве приложение загружает историю, общий XP, полученные достижения и лучшие рекорды аккаунта. Активный черновик не переносится: он остаётся на устройстве, отдельно для каждого аккаунта.
- Смена аккаунта создаёт новое защищённое дерево приложения и использует другой локальный ключ. Сервер и пользователь входят в ключ владельца; токен и пароль в данные прогресса не записываются. Поздний ответ после смены сессии не принимается.
- Уровень вычисляется из общего XP на клиенте по шкале levels-v1.md, отдельное поле уровня не синхронизируется. Продолжение шкалы после 10-го не меняет баланс XP.
- Спорт по умолчанию остаётся локальной настройкой каждого устройства и аккаунта, специализация/описание по-прежнему серверный профиль.

## Обновление рабочего сервера

Сначала сохранить закрытую резервную копию `server/pb_data` при остановленном PocketBase. Затем обновить код и запустить:

```powershell
cd D:\Developments\sport_platform
powershell -ExecutionPolicy Bypass -File .\server\start.ps1
```

Если сервер уже работает, остановить его через Ctrl+C в его окне перед повторным запуском. Скрипт применяет новую миграцию `1794268800_account_progress.js` и явно подключает `server/pb_hooks`. Старые миграции не редактировались. Новую коллекцию и данные рабочего сервера помощник не создавал: всё проверяется на отдельной временной базе. После обновления полностью перезапустить Flutter-приложение. До обновления синхронизация не считается успешной; локальные записи остаются в очереди.

## Формат хранения и перенос

- Локальный ключ: `pace_progress_v2:<encoded server|accountId>`. Отдельный черновик: тот же ключ с `:draft`. Служебный `_sync` содержит исходные новые тренировки, ещё не подтверждённый перенос старой истории, последнюю принятую ревизию и время синхронизации.
- Старые `pace_local_data` и `pace_active_workout` сохраняются как резерв. Одноразовый маркер `pace_progress_legacy_owner` закрепляет их за первым подходящим аккаунтом. Если ранее `pace_profile_legacy_owner` уже указал другого владельца, чужой аккаунт историю не присваивает.
- Тренировки без sessionId получают стабильный SHA-256 идентификатор содержимого. Повторный перенос той же истории не создаёт дубликатов. Первое наполнение пустого серверного прогресса сохраняет прежний XP в точности и не добавляет XP задним числом за исторические достижения.
- При переносе в уже заполненный аккаунт добавляются только неизвестные тренировки; общие награды объединяются. Разница между старым балансом и суммой старых тренировок сохраняется как одноразовый `legacyCredit`, чтобы прежний дополнительный XP не начислить дважды с разных устройств. При пересечении историй итог может отличаться от простого сложения двух старых балансов из-за удаления повторных наград.
- Серверная коллекция `pace_progress`: одна запись на владельца, уникальный owner, числовая revision, JSON snapshot. Обычный collection CRUD закрыт; доступны только маршруты своего прогресса. Снимок включает полную историю с GPS-маршрутами, баланс, достижения, рекорды и маркеры переноса. `_sync` на сервер не отправляется.

## Объединение и повторные запросы

`GET /api/pace/progress` возвращает `{revision, data}`. Отсутствующая запись — `{revision: 0, data: null}`. `PUT` принимает ожидаемую revision и новый data, проверяет принадлежность по токену `pace_users` и обновляет снимок в транзакции. Несовпавшая версия возвращает 409. Существующие sessionId удалять нельзя; редактирование/удаление тренировок в эту версию не входит.

Клиент читает актуальное состояние, добавляет только неизвестные сессии из очереди и пересчитывает их награды относительно уже принятой истории. Базовый XP каждой новой тренировки сохраняется; обычные ступени выдаются один раз, рекорды — первый результат 50 XP, последующие строгие улучшения 100 XP без лимита. Несколько устройств не получают повторный XP за одну обычную ступень. Для записей, отправленных офлайн позднее, рекорд сравнивается с уже принятым серверным лучшим временем; локальная награда до синхронизации может скорректироваться. Совпадение sessionId идемпотентно.

При 409 клиент заново загружает состояние и повторяет объединение, максимум четыре попытки за проход. Потерянный ответ после успешной серверной записи безопасен: повтор не добавляет тренировку/XP. Ответ проверяется на наличие отправленных sessionId и подтверждённого переноса перед очисткой очереди.

Сеть не удерживает локальную очередь записи. Если новая тренировка завершилась во время загрузки, подтверждение первого пакета сохраняет новую очередь и пересчитывает её относительно ответа; запускается следующий проход (до четырёх пакетов за вызов). Если сеть или локальная запись подтверждения не удалась, данные остаются для следующей попытки.

У SharedPreferences кэш меняется до подтверждения платформенной записи. При неудачной записи хранилище перечитывает сохранённые значения; если перечитать не удалось, чтение прогресса блокируется до успешного восстановления кэша. Это предотвращает ложное завершение по несохранённому кэшу. Ответ сервера с меньшей ревизией или без уже подтверждённых локальных тренировок также не затирает локальную историю: синхронизация останавливается с сообщением о неполной серверной истории.

## Границы текущей версии

- Это закрытая альфа: расчёт XP и объединение выполняются клиентом, сервер обеспечивает авторизацию, атомарную ревизию и сохранение. Защита от намеренной подмены собственного XP и авторитетный серверный расчёт перед соревнованиями — отдельный этап.
- Снимок и запрос ограничены 32 MiB. В браузере есть отдельный лимит локального хранилища. Постраничная загрузка, отдельные серверные записи тренировок и оптимизация хранения GPS нужны перед большой историей и массовым запуском; превышение лимита не должно подтверждать отправку или очищать очередь.
- Серверные резервные копии по-прежнему обязательны. Синхронизация не заменяет резервную копию `pb_data`. Публичный HTTPS-доступ и фоновые задачи ОС вне открытого приложения не добавлялись.
- Бассейн, сравнение одинаковых трейловых маршрутов и новые правила удаления тренировок не добавлены. Рабочая база/телефон этим этапом не проверялись, приложения Android/iOS не собирались.

Реализация опирается на официальные API PocketBase 0.41.1: [маршруты и авторизация](https://pocketbase.io/docs/js-routing/), [записи](https://pocketbase.io/docs/js-records/), [транзакции](https://pocketbase.io/docs/js-database/). Проверка миграции, приватности и гонки ревизий выполняется реальным временным PocketBase в `test/account_api_integration_test.dart`; локальная очередь/перенос/слияние и UI проверяются отдельными Flutter-тестами.
