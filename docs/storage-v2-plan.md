# PACE — отдельное хранение тренировок V2

12 ноября2026 пользователь одобрил SQLite на устройстве, отдельные серверные записи тренировок/телеметрии, отправку новых тренировок вместо общего JSON, страницы истории и загрузку трассы при открытии. Пользователь разрешил удалить все прежние тренировки вместо переноса и уточнил: запись PACE и новые тренировки Garmin. Вместе с удаляемой историей обнуляются связанные XP/достижения/рекорды и результаты зачёта; аккаунты/профили/специализации/клубы сохраняются. До очистки рабочей базы обязательна проверенная резервная копия; старую очередь Garmin нельзя вернуть в новую историю.

## Решение

- Production `LocalStorageService.forAccount` переключается на SQLite. Старый адаптер SharedPreferences остаётся для совместимости существующих тестовых хранилищ; рабочие тренировки туда больше не записываются и из него не импортируются.
- Локальные таблицы: state(owner,epoch,revision,derived,selectedSport), workouts(owner,sessionId,summary,pending), telemetry(owner,sessionId,kind,json), drafts(owner,json). Все операции scoped по серверу+аккаунту, завершение и outbox атомарны. Только первая страница metadata загружается в главные экраны; totals/награды отдельно; телеметрия по запросу.
- SQLite: sqflite2.4.6 для Android/iOS, sqflite_common_ffi2.4.7 для desktop/tests, sqflite_common_ffi_web1.2.2 для web. Версии закреплены pubspec.lock. Worker собран из официального web/sqflite_sw.dart пакета1.2.2 командой Dart compile js -O2; штатный setup не завершился из-за окружения webdev/build_daemon. WASM взят из указанного setup релиза sqlite3.dart sqlite3-3.6.0. Оба runtime-файла включены в web/. Источники: https://pub.dev/packages/sqflite , https://pub.dev/documentation/sqflite_common_ffi_web/latest/ , https://github.com/simolus3/sqlite3.dart/releases/tag/sqlite3-3.6.0 .
- V2 сервер: собственная epoch, отдельный state без workouts, отдельные summaries и приватные chunks телеметрии. GET /api/pace/v2/state; POST /api/pace/v2/workouts для list/stage/commit/detail. Страницы ограничены20, chunks ограничены по размеру. Сначала stage телеметрии, затем атомарный commit summary+derived с CAS revision; sessionId и fingerprint обеспечивают идемпотентность. Это транспорт/целостность, не античит.
- Новые данные не содержат legacy-credit. Старые API прогресса в production закрываются кодом426, старая версия не сможет вернуть удалённую историю. Операторский флаг PACE_ENABLE_LEGACY_API=1 допускается только в изолированных старых тестах; рабочие launcher его не задают.
- Multi-device: чтение состояния и страниц summaries до зафиксированной revision, объединение с текущим outbox, повторное начисление pending относительно серверного состояния, отправка каждой новой записи отдельно. При CAS-конфликте повтор с новым state, после подтверждения summary/телеметрии outbox очищается. Прерванный upload не теряется и не удваивает XP.
- AchievementProgress получает сериализуемые агрегаты; рекорды рассчитываются только на новой трассе, best сохраняется отдельно. UI достижений/рекордов берёт полные totals/best, не историю первой страницы. История загружается20порциями, подробности получают локальную/серверную трассу по sessionId.

## Воспроизведение web SQLite smoke

Создать build/webprobe, скомпилировать `dart compile js -O2 tool/web_sqlite_probe.dart -o build/webprobe/main.js`, скопировать web/sqflite_sw.js и web/sqlite3.wasm в build/webprobe. Записать index.html с body и `<script defer src="main.js"></script>`. `node tool/test_web_sqlite.mjs` запускает локальный HTTP и headless Chrome с временным профилем, проверяет транзакцию, закрытие/повторное открытие и чтение из SQLite. CHROME_EXE позволяет указать другой Chrome. Реальный профиль браузера и рабочие данные не используются.

## Применение

После проверок: `powershell -NoProfile -ExecutionPolicy Bypass -File server/deploy-storage-v2.ps1 -ApplyFreshStart`. Скрипт рассчитан только на подтверждённый путь D:\Applications\PACE\Project и отказывается повторно сбрасывать уже применённую V2. Останавливает только два PACE-задания, закрывает ingress и ждёт завершения возможного Garmin collector через эксклюзивный файловый lock. Создаёт закрытую остановленную копию pb_data и файлов Garmin, сверяет SHA256 и quick_check; репетирует миграцию на отдельной копии. Сравнивает полные строки пользователей/клубов/событий/членства по хешу, затем фиксирует новый Garmin cutoff и очищает очередь без изменения ключа/привязки. После запуска проверяет сохранённые строки и пустую историю, запускает шлюз. Если проверка до старта завершилась ошибкой, службы остаются остановлены для исправления; нельзя запускать новую миграцию без проверенной копии. Секреты остаются только в закрытой резервной копии, не в Git. Откат удаления — восстановление всей остановленной pb_data и приватного Garmin набора из этой копии вместе с исходниками прежнего протокола; нельзя смешивать V1 сервер и V2 клиент.

Ограничения: staging незавершённых телеметрий ограничен64MiB на аккаунт (история опубликованных тренировок этим лимитом не ограничена). Одна часть≤128KiB/500отсчётов, запрос≤256KiB, manifest≤2048частей; списки≤20, detail≤4частей. Garmin Personal API пока использует прежний локальный inbox≤200активностей/30MiB и ограничения одного FIT; очередь подтверждений/архивирования Garmin — отдельный будущий этап. На телефоне сборку ещё нужно проверить. Холодный offline-вход и античит не реализованы этим переносом.
